01 Qué se apoya en qué

La spec funcional cubre la etapa 3 y da por resueltas las etapas 1 y 2. Esas etapas existen y son navegables hoy: son el multicotizador de infinito.foxia.ar. Recorrí sus endpoints para confirmar qué entrega exactamente en la frontera.

02 Qué hay del otro lado

Recorrí el embed del multicotizador para ver qué expone. El resultado cambia la arquitectura del front nuevo.

Es Django + htmx server-rendered. No hay API JSON: /api/, /api/schema/ y /openapi.json devuelven 404, y el endpoint de parciales responde text/html aunque se le pida JSON explícitamente. Toda la navegación es intercambio de fragmentos HTML.

Eso resuelve de paso la ambigüedad 7.8 de la spec: la fecha de nacimiento y el CP que aparecen en S12 sin haberse capturado vienen de acá. El motor ya pide provincia y localidad, y el CP viaja con la cotización — es el mismo que S06 muestra como read-only.

⚠ El reCAPTCHA está desactivado en producción

En /static/js/recaptcha.js, la validación real está comentada y reemplazada por un bypass que siempre devuelve éxito:

async validateRecaptcha(action, sessionKey) {
    // BYPASS: Desactivar reCAPTCHA para desarrollo
    sessionStorage.setItem(sessionKey, 'true');
    return { success: true, cached: false };
    // CÓDIGO ORIGINAL COMENTADO - Descomentar para producción

El endpoint /embed/validate-recaptcha/ existe y la site key se sirve en el HTML, pero el cliente nunca lo llama. El motor de cotización queda abierto a automatización. Tiene toda la pinta de un bypass de desarrollo que se fue a producción; conviene revisarlo con independencia de este proyecto.

03 Arquitectura

Decidido: un BFF propio envuelve el motor htmx y le sirve JSON al front. El front nuevo nunca habla htmx.

El riesgo asumido es que el BFF parsea HTML: si Foxia cambia el markup, se rompe. Conviene aislar el parseo en un solo módulo con tests contra fixtures del HTML real, para que un cambio de markup sea una corrección localizada y no una cacería. A mediano plazo, pedirle a Foxia una API JSON sigue siendo la salida correcta.

Responsive

El Figma es todo mobile y la spec lo confirma, pero el CSS de producción del multi ya es mobile-first con breakpoints en 768 y 1024 y un contenedor que arranca en 408 px. Las pantallas nuevas siguen esa misma escalera: misma columna centrada que se ensancha, sin layout de escritorio propio. Así el salto entre etapa 2 y etapa 3 no se nota.

06 Qué falta decidir

La spec lista once ambigüedades. Estas son las que bloquean el arranque, más dos que el relevamiento del export y del motor agregan.

bloqueante
La rama 0 KM saltea las 9 fotos

Spec 7.3. Es la decisión de mayor impacto: si un 0 KM se emite sin inspección, cambia el modelo de datos, la validación de emisión y probablemente el acuerdo con la compañía. Hay que resolverlo antes de tocar el wizard.

bloqueante
¿Quién completa los datos de la agencia?

S02 pide agencia, vendedor, teléfono y mail, y es la primera pantalla del formulario. Si lo carga el vendedor, la app necesita sesión y la etapa 3 es B2B; si lo carga el cliente, hay que explicarle por qué se lo preguntan. Define el esqueleto de la app y no está en la lista de la spec.

bloqueante
Dónde entra la verificación manual

Cotizador 23 existe pero no está en el mapa. Si S12 puede derivar a emisión asistida en vez de emitir, el front necesita ese estado y el backend necesita decidirlo. Hoy no está especificado en ningún lado.

a definir
Estados de error: ninguno está maquetado

Spec 5.3. Ni campo inválido, ni archivo > 4 MB, ni extensión rechazada, ni fallo de emisión, ni loading del «Confirmar datos». Son del orden de 20 estados y hoy no hay diseño para ninguno.

a definir
Textos de los 9 ítems de foto

Spec 7.5. El prototipo sólo maquetó «Lateral conductor». Faltan título, tip e imagen de ejemplo de los otros 8, y decidir si el chip «?» va en los 9 o sólo en 5.

a definir
Catálogos de los selects

Spec 7.4. Sexo, condición fiscal, marca de tarjeta y tipo de cuenta. Ninguno está desplegado. Además condición fiscal se dibuja como input pero se comporta como select.

a definir
Destino de los dos botones de WhatsApp

Spec 7.1. ¿Número fijo de CE Brokers o el del vendedor de la agencia? ¿El mensaje prearmado lleva el ID de cotización? Con S02 capturando el teléfono del vendedor, la segunda opción es viable.

a definir
Nombres inconsistentes de los ítems de foto

Spec 7.6. «Tablero de contacto» vs «Tablero en contacto», «Cédula verde/ título» vs «Cédula verde título». Un enum único y las etiquetas derivadas de él.

menor
PDF como foto del vehículo

El modal acepta .pdf para las 9 tomas. Tiene sentido para la cédula verde, no para el lateral del auto. Conviene restringir formatos por ítem.

resuelto
De dónde salen la fecha de nacimiento y el CP

Spec 7.8. Del motor: las etapas 1–2 ya capturan provincia, localidad y CP, y viajan con la cotización. La inconsistencia CP 1234 vs 3000 es del mockup, no del flujo.

07 Por dónde empezar

La spec propone un orden razonable. Este lo ajusta a lo que sabemos del motor: lo primero no es maquetar, es probar que el BFF puede sostener la traducción.

  1. Prototipo de parseo del BFF

    Un solo step del motor traducido a JSON, con fixtures del HTML real y tests. Si esto es frágil, conviene saberlo antes de construir trece pantallas encima.

  2. Design system con los tokens de §04

    theme.extend de Tailwind con los hex reales, más C1–C10 de la spec y sus estados. Los valores ya están confirmados: no hay que volver a Figma.

  3. Máquina de estado del wizard

    El modelo de datos de la sección 6 de la spec, con borrador persistido en cada paso. Trece pasos y nueve uploads no toleran perder progreso.

  4. S02 → S07

    Las seis pantallas de formulario: mismo patrón, ninguna sorpresa.

  5. Módulo de fotos S08 → S10

    Lo más complejo: uploads, validación de tipo y tamaño, progreso, reintentos. Se implementa una vez y se reusa.

  6. S11 con máscaras y validaciones

    Luhn para la tarjeta, 22 dígitos para el CBU. Ojo con el placeholder de la spec, que trae 16.

  7. S12, S13 y la rama de verificación

    Resumen con edición inline, emisión y —si se confirma— la derivación a emisión asistida de Cotizador 23.

  8. Estados de error

    Recién cuando diseño los defina. Hasta entonces, placeholders explícitos y no comportamiento inventado.

Los pasos 1 y 2 pueden arrancar hoy: no dependen de ninguna de las decisiones abiertas. El paso 3 necesita resuelto el 0 KM, porque cambia el modelo de datos.
